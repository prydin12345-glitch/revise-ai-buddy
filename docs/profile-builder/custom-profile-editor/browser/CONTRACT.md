# Controlled persistence boundary

`FixtureApp` mounts production `ExamProfileModal`, calls `buildCustomProfilePayload` used by SubjectDetail, and invokes the actual `useSubjectProfiles` mutations and tier persistence. The full SubjectDetail page is not mounted. Its read cache is seeded with synthetic owned rows; opening the modal needs no database reads. A strict in-memory Supabase-shaped adapter replaces the client. It permits the profile table, requires an explicit owned ID for updates, and blocks other tables, functions, RPC, storage and channels. This tests the client workflow, not deployed database RLS.

The save contract is the actual eight modal callback arguments and `ProfileSaveResult` (`ok`, optional `message`/`profileId`). Reopening reads the stored row instead of the edited draft. A partial create retains the returned ID for update on retry; the transfer test exercises the hook's tier failure and proves only one insert succeeds. No helper, callback payload or raw topic array is coerced to make assertions pass.

Profiles, owners, studied texts, metadata and timestamps are fictional. Rich custom fixtures include a saved topic absent from the library, aliases, custom qualification, unknown assessment tier, null timing, mixed calculator, exact sections with optional answers, unknown question metadata, response/visual flags and a custom snapshot. Guided topics come from production plan parts with versioned metadata. Legacy fixtures retain zero written questions, MCQ-only structure and null blueprint/timing. Raw-topic coverage includes whitespace, duplicates, case variants, a literal link and an empty legacy value.

Unexpected HTTP/WebSocket requests fail the browser run. No live account, student data, source retrieval, AI/provider call, backend endpoint, install or download is used. Font reuse is read-only from `/tmp/profile-builder-style-cleanup/fonts`; artifacts belong to `/tmp/profile-builder-custom-profile-editor`. Existing AI and style-cleanup harnesses/artifacts are untouched.
