# Assessment identity, page selection and manual component codes

Baseline: `51da022b` (the merged practice-route correction plus the current development dependency update). This change keeps one source-backed profile per selected assessment. The owned document index supplies the paper choices and is reused within that build; it does not generate every paper in the syllabus together.

## Confirmed causes

The assessment menu was produced by a deterministic parser, before AI extraction. Its grouping key contained the full display label. A named paper followed by AO weighting columns became another identity; a title wrapped onto a second line could remain truncated; those variants then prevented the bare paper number from collapsing into its detailed entry. The duplicate representations could also trigger the request for an assessment-overview page. Selecting a different variant changed the matching input, so the old variants were not guaranteed to produce identical profiles.

The initial document scan and explicit page follow-up applied different qualification requirements. Source-backed Edexcel titles such as “Pearson Edexcel Level 3 Advanced GCE in Business” were not recognized as A-level anchors. A valid shared overview could consequently pass initially and fail when the user selected it. The old page message described every discarded result as an unmatched page, including results blocked for a different scope or capacity reason.

The component-code field had another client-side restriction: a selected source assessment without a discovered code rejected every manually entered code. A correct student reference could not reach source checking. Replacing the assessment identity with that unverified code would also make source matching unreliable.

The actual private Business PDF and failed live request were not attached to this task. Regression fixtures use the reported titles and original synthetic Edexcel-shaped pages, including a physical page 14 shared by Papers 1 and 2. They establish these code paths without claiming to replay the private file or a real model response.

## Resulting behavior

- Discovery separates `canonicalComponent` from the display title. Explicit source codes take precedence; otherwise only a uniquely supported scoped numbered identity can use its short paper/unit/component name. Candidate IDs bind source checksums, course, board, qualification and subject. Client aliases cannot grant source authority.
- Strong weighting-column suffixes and safely identifiable wrapped titles are normalized for presentation and duplicate matching. Repeated appearances contribute aliases and literal citations to one assessment. Genuine conflicts, different component codes, qualification variants and ambiguous optional assessments remain unresolved.
- The backend reconstructs the selected assessment from the owner's actual upload, including before accepting cached evidence. Only unique server-derived source aliases are used for retrieval. Unknown IDs, a code belonging to another discovered assessment and conflicting source identities block before provider work.
- Initial and follow-up retrieval use the same full-document qualification context. A page answer narrows the original literal spans and retains the relevant course anchors. Same-page assessment blocks and their continuations across physical page breaks remain separate. A paper-specific calculator/time/instruction paragraph does not become shared at a page break. Only explicit content allocations and genuine course-wide section evidence can supply shared scope.
- Follow-up status distinguishes missing assessment text from located evidence blocked by scope or reading limits. Physical PDF page numbers and printed page labels are shown separately where the source supplies a label.
- An unknown component code can be confirmed in a dialog for an attached syllabus. Cancel and Escape restore the previous confirmed reference while keeping the builder, selection and files open. A blank code remains allowed. Changing the assessment or source requires confirmation again; an explicit known-code mismatch remains an error.
- A confirmed code absent from the source remains a **user-entered reference**, not verified evidence or an approved assessment identity. It is retained on the owned job and, after validated drafting, in an explicit `designDecisions` annotation on the saved template. Resume and reopening the saved profile restore it. Confirmation cannot replace missing marks, topics, duration, source quotations or full-mock requirements. Model-authored imitations of the reserved annotation are removed.
- Changing only a manual reference does not require another model extraction of reusable owned evidence. Request hashes still bind the actual confirmation, and each new upload selection is checked. Existing owner, lease, revision, quota and bounded-call safeguards remain authoritative.

The new manual-reference flow applies to uploaded sources. Other source modes do not silently accept and discard a reference that their request contract cannot retain. Existing profiles, presets, grades and attempt snapshots are not rewritten; no database migration is required.

## Verification and activation

The baseline had added two Lovable development plugins to `package.json` and `bun.lock`, but omitted them from `package-lock.json`; `npm ci --dry-run` therefore rejected the clean-install state. The npm lockfile is synchronized with those existing declarations, recording `@lovable.dev/vite-plugin-dev-server-bridge` 1.3.3 and `@lovable.dev/vite-plugin-hmr-gate` 1.8.2. No existing locked package was upgraded and the installed dependency tree was not replaced. The clean-install dry run now passes; this repairs the baseline's lockfile rather than adding a new application dependency choice.

`npm run check` passes **3,379 tests in 202 files**, app and strict shared Physics type checking, critical lint, 39 function identifier/bundle checks and the production build. Actual Deno 2.5.6 checking passes for both affected function entry points. The focused tests include 42 discovery cases, 96 document-index cases, 12 actual job-flow cases and 42 builder-resolution/UI cases.

The [before/after replay](before-after.json) applies the actual old and new parser/index to an original synthetic source with the reported Business titles. The baseline produces ten choices, false ambiguity and a rejected physical page 14; the correction produces three choices without ambiguity and retains Paper 1 facts from the shared page while excluding Paper 2 facts. This is an offline regression control, not the user's private PDF or a real extraction response.

The [verification record](verification.json) records the check results. The [offline browser harness](browser/README.md) uses the actual builder and local source inspection with synthetic API responses; it does not verify live service behavior, physical mobile devices or real AI extraction quality. The final frozen run passes **48 scenario groups across eight viewport/theme cases**, including native confirmation, Cancel/Escape and restart behavior. Strict hashes match **829 application/config files, 189 server/config files and 1,743 installed dependency inputs** in both the relocated snapshot and working checkout. [The browser results](browser/results/browser-results.json) and [hash record](browser/results/hash-verification.json) remain separate from backend job and evidence regressions; four selected screenshots received visual inspection.

The [actual import graph](edge-function-dependencies.json) checks all 39 Edge Function entry points and identifies **two affected functions**: `profile-builder` and `extract-exam-questions`. [The deployment handoff](deployment.md) requires both from the same reviewed revision and a matching preview. The previous strict backend request schema rejects the new optional selection/reference fields, so a newer preview alone does not establish compatibility. The client reports that failure without silently dropping a confirmed code or retrying paid work.

No deployment, paid AI call, student login, live-data write, migration or website publication is performed by these changes. Live deployed revisions and database grants are not verified by repository tests.
